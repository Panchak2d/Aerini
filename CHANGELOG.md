## [Unreleased]

### Added
- Canvas (desktop): **Undo** and **Redo** buttons in the toolbar, with a tooltip naming the step each one will undo or redo, and a status-bar message after each. Renaming a node, enabling or disabling it, choosing its saved credential, and changing its settings can now be undone (typing in one field is a single step), where before only adding, deleting, moving, and wiring could. `Ctrl+Shift+Z` now works for Redo on every keyboard (Caps Lock, non-Latin layouts). See [Keyboard shortcuts](docs/guide/keyboard-shortcuts.md)
- AI Memory: a conversation can now remember the files shared in it, so an AI node keeps seeing them on later messages instead of only on the message that carried them. Set **Files** (e.g. `{{Webhook.output.files}}`) on `append` or `write` to store files with a message, and turn on **Include Files** to get them back as a `files` output you can wire to an AI node's Files port; a new `forget_files` operation deletes a session's files and keeps its messages. Both are off by default, so existing workflows behave as before. Limits: png, jpeg, webp, gif, pdf, txt and md only; 3 MiB per file; 20 files and 32 MiB kept per session (**Max Stored Files**); at most 5 files (**Max Files**, up to 20) and 12 MiB returned per read, drawn from messages inside **Max Messages**. Files are kept or dropped whole, oldest first, and identical files are stored once. `clear` (including the Chat panel's Clear and session delete), `write`, and pruning past **Max Stored** now delete the files with their messages. Remembered files are stored unencrypted in `ai_memory.db`, are sent to the AI provider again on every run that wires them in, and are copied into run history with the node's output. Adds an `ai_memory_files` table, created on first use, to `ai_memory.db`; existing data is untouched and no migration runs. See [Nodes Reference](docs/guide/nodes.md#remembering-files) and [Chat Panel](docs/guide/chat-panel.md#attachments)
- Chat panel: a banner above the messages now flags wiring that would make replies fail or ignore attached files — files that no node reads, or a node that uses another node's output without running after it — and fixes the common cases in one click (**Connect to** an AI node, **Connect them**); a running workflow picks the fix up on its next run, with no restart. It replaces the short-lived "no node reads them" notice shown after sending files. Connections made this way can be undone with `Ctrl+Z`.
- Desktop: in-app updates. **Settings → About → Updates → Check for Updates** shows a newer version, and **Install and restart** downloads it, verifies its signature, installs it, and restarts, with a progress bar and a Cancel button. Updating is still click-only (nothing is checked in the background), Aerini asks before stopping running workflows or when changes may be unsaved, and where an in-app install isn't possible it links to the release page instead. Aerini 0.4.1 and earlier can't update themselves, so install the first release that includes this by hand once. See [Updating](docs/operations/updating.md#desktop-app) and [Security](docs/guide/security.md#updates-and-the-network)
- `aerini-server` (`api`) and the desktop app: `scheduler-status` events now include a `trigger_type` field (`interval`, `cron`, `once`, `webhook`, `manual`, or `plugin`), so a client can tell what kind of trigger a job has without reading its stored trigger; the field is additive and existing clients are unaffected. See [Events](docs/operations/server-api-reference.md#events-sse)
- Chat panel: files attached to a sent message now appear as filename chips in that message, and are saved with the session, so they are still shown after switching sessions or restarting the app. Adds a nullable `attachments_json` column to the local chat-message table (local database version 9, unrelated to a workflow file's `schema_version`; existing messages are unaffected); see `docs/guide/chat-panel.md#attachments`
- Webhook: a request body with an `attachments` array (as the desktop Chat panel sends when files are attached) is now also exposed as a top-level `files` output, so `{{Webhook.output.files}}` can be wired to a Files input such as AI Prompt's; `body.attachments` is unchanged, and `files` is omitted when the body has no `attachments` array. Applies to both ad-hoc Run and background (scheduler-driven) runs; see `docs/guide/nodes.md#webhook`
- Chat panel: you can send attachments without any text (the message is posted to the webhook as an empty string), and clicking a sent file chip opens an image full-size or downloads any other file; see `docs/guide/chat-panel.md#attachments`
- Execution Transcript: clicking a log line that's tied to a specific node now selects that node on the canvas, the same way clicking a run-history entry does; keyboard-accessible via Enter/Space when the line is focused
- `aerini-server`: a prebuilt container image is now published to GHCR (`ghcr.io/panchak2d/aerini-server`) on every tagged release, tagged with the release version and `latest`; `docker pull` replaces cloning the repo and building the image yourself as the fastest way to get a working binary. See [Server Deployment](docs/operations/server-deploy.md#getting-the-aerini-server-binary)
- Plugins: a trigger plugin can now export `metadata` (icon, author, version) by targeting the new `aerini-node-with-trigger-and-metadata` world; plugins built against `aerini-node-with-trigger` load unchanged. Trigger-capable plugins are listed under **Triggers** in the node palette, next to Schedule and Webhook, with their Plugin badge; see `docs/development/plugin-authoring.md#trigger-plugins`
- Plugins: a trigger plugin can now report when its next event is due, so the Background Runs panel shows "next in Ns" for it, by targeting the new `aerini-node-with-trigger-and-next-fire` world and calling its `trigger-schedule` import; reported times are validated and never affect scheduling. Plugins built against any earlier world load unchanged and keep showing "running", and the bundled heartbeat example now reports its next beat. See `docs/development/plugin-authoring.md#showing-a-countdown-to-the-next-event`

### Changed
- **Breaking** for workflows that read an unrelated node's output out of a Merge result (all runs, including `aerini-server` and `api`): Merge now returns only the outputs of the nodes wired into it whose connection fired, where it used to return every output produced so far in the run. A node on a branch that was not taken, a failed or skipped node, and a node that is not connected to the Merge no longer appear in the `object` keys or the `array` values, so an `array` index that counted an unrelated node now points at a different value. Wire that node into the Merge, or read its output directly with an expression such as `{{NodeName.output}}`. None of the shipped examples are affected. See [Nodes Reference](docs/guide/nodes.md#merge)
- **Breaking** for muscle memory (desktop app): dragging from either end of a wire no longer picks it up and disconnects it on release. Drag from a wired input, or click the wire and drag the ring on its input end, to move it to another input; dropping anywhere else cancels, and `Esc` cancels mid-drag. Dragging from an output always starts a new wire. To disconnect a wire, click it and press `Del`, or right-click it. A moved wire can be undone with `Ctrl+Z`. See [Keyboard shortcuts](docs/guide/keyboard-shortcuts.md)
- **Breaking** for workflows that wire several sources into one input (all runs, including `aerini-server` and `api`): an input port now accepts one connection unless it is multi-input, and Merge's input is the only multi-input port built in. A workflow that breaks this fails with `PortArityViolation` before any node runs, where it used to run. The desktop canvas already refused a second wire, so only imported, hand-written, AI-generated, or API-submitted workflows are affected; none of the shipped examples are. Route the wires through a Merge node instead. The desktop app opens such a file with every connection intact, marks the input in red, and warns once. See [Workflow File Format](docs/reference/workflow-file-format.md#input-port-arity)
- Canvas (desktop): ports now respond to drags rather than presses. Nothing happens until the pointer moves a few pixels, so clicking an output or an empty input no longer opens the node search; dropping a wire on empty canvas still does. Drag from an empty input to wire backwards to an output (or to a new node), hold `Ctrl`/`Cmd` while dragging from an output to move every wire leaving it onto another output as one undo step, and drop a wire on an input that already has one to replace it, with one `Ctrl+Z` to undo and a notice naming the replaced source; before, the drop did nothing. See [Keyboard shortcuts](docs/guide/keyboard-shortcuts.md)
- Running workflows: editing a workflow while it runs in the background now saves right away, and wiring or node-setting changes apply from the next run without a restart; a run already in progress finishes with the version it started with. Only the trigger (Schedule timing, Webhook port, path, method, secret and dedup window, a trigger plugin's settings, or the trigger node itself) is fixed when the job starts. A trigger edit shows **Restart to apply trigger** in the status bar and a **Restart** button in the Chat panel, which now asks before stopping a run in progress; before, the Chat panel asked for a restart after every one-click wiring fix, which stopped any run in progress. If autosave fails while a workflow runs, the status bar shows **Not saved**. See [Background Runs](docs/guide/background-runs.md#editing-a-workflow-while-it-runs)
- Desktop: Check for Updates now reads the update manifest of the latest published release instead of asking GitHub's Releases API, so a release appears only once it is published, and prereleases are never offered. A known side effect on macOS: because the app isn't signed with an Apple Developer certificate, an update can make macOS ask for Keychain access again; see [Known Issues](docs/known-issues.md#macos-asks-for-keychain-access-again-after-an-update)
- **Breaking** for Wait nodes in `condition` mode: the condition is now checked once, when the node starts. A match leaves through **Done**; a mismatch leaves through **Timed out** immediately instead of sleeping up to `timeout_secs` first, because upstream outputs cannot change while the node runs. `poll_interval_secs` and `timeout_secs` are still accepted so saved workflows load, but no longer have any effect. See `docs/guide/nodes.md#wait`
- **Breaking** for existing cron schedules (Schedule node, `cron` mode): when both day-of-month and day-of-week are restricted (neither starts with `*`), a day now matches if either does, as in standard cron. `0 9 1 * MON` runs on the 1st and every Monday; before, it ran only when the 1st fell on a Monday. A field starting with `*`, such as `*/2`, still requires both to match. Review any schedule that restricts both fields. See `docs/guide/nodes.md#schedule`
- **Breaking** for scripts that grant workflows to admin tokens, or create tokens that expire at once (`aerini-server`, `api`): `POST /api/tokens/:id/workflows/:workflow_id` now returns `400` when the target token has the `admin` scope, and `POST /api/tokens` returns `400` for `expires_in_secs: 0`. An admin token ignores the workflow ACL, so the grant used to succeed and report a restriction that was never enforced, and a zero lifetime created a token that could never authenticate. See [Per-token workflow ACL](docs/operations/server-api-reference.md#per-token-workflow-acl)
- **Breaking** for scripts that create admin tokens with grants (`aerini-server`, `api`): `POST /api/tokens` now returns `400` when `scopes` includes `admin` and `workflow_ids` is non-empty. Admin tokens ignore the workflow ACL, so the request used to succeed and report a restriction that was never enforced. Drop `admin` to get a restricted token, or drop `workflow_ids` for an unrestricted admin one. See [Per-token workflow ACL](docs/operations/server-api-reference.md#per-token-workflow-acl)
- Monitor: a Webhook or trigger-plugin workflow that is waiting for a request or event now shows **Listening** in place of a running time that counted up from when it was armed; a plugin that reports its next event keeps its countdown. See `docs/guide/monitor.md#the-workflow-list`
- Monitor: the **Scheduled** filter now lists every workflow running in the background with a Schedule, Webhook, or trigger-plugin trigger, including Webhook and plugin triggers that have no next fire time; before, it showed only rows with a countdown. A stopped workflow no longer keeps showing a stale countdown after it is started again. See `docs/guide/monitor.md#filtering-the-list`
- **Breaking** for scripts that rely on silent success (`aerini-server`, `api`): `POST /api/tokens/:id/workflows/:workflow_id` now returns `404` for an unknown or revoked token instead of `201`, and `DELETE /api/tokens/:id` returns `404` for an unknown token instead of `200`, so a mistyped token ID no longer looks like a token that was restricted or revoked. Revoking an already-revoked token still returns `200`. See [Token management](docs/operations/server-api-reference.md)
- `aerini-server` (`api`): `POST /api/tokens` rejects an empty `scopes` list, a blank label, and `workflow_ids` beyond 500 entries or 256 characters each; `POST /api/credentials` rejects a blank `id` or `name`, an empty `value`, and an `id` or `name` over 256 characters. Each returns `400` with a message.
- Building from source now requires Rust 1.96 or later (was 1.94.1 for `aerini-server`, 1.95 for the desktop app), set by Wasmtime 49
- **Breaking** for an existing desktop install: the app identifier changed from `com.aerini.app` to `org.aerini.desktop` (the old one ended in `.app`, which conflicts with the macOS bundle extension), so the app's data folder moves to a new location, listed in [Installation](docs/getting-started/installation.md). A copy already on your machine starts empty; to keep your workflows and settings, quit Aerini and move the contents of the old folder into the new one. The credential encryption key lives in the OS keychain under a fixed name, so moved credentials still decrypt
- **Breaking** for pages that call `POST /api/widget/:workflow_id/mint-token` from browser JavaScript (`aerini-server`, `api`): the server no longer allows any origin, including localhost and `--allow-origin` ones, cross-origin access to that endpoint, so the browser blocks the call. It was already documented as server-to-server only; call it from your backend, which sends no `Origin` and is unaffected. See [Embeddable Chat Widget](docs/guide/widget-embedding.md)
- `aerini-server` (`api`): CORS now exposes `Retry-After` to browsers, so a client on an allowed origin can read it from a `429`, and preflight answers are cacheable for an hour, which cuts repeat `OPTIONS` requests. The embedded chat widget shows the retry delay when it is rate-limited.
- **Breaking** for tokens with workflow grants (`aerini-server`, `api`): the per-token workflow ACL now confines a token on every workflow route, not only the scheduler, memory, performance and event routes. A restricted token gets `403` on `GET|DELETE /api/workflows/:id`, `POST /api/workflows/:id/run` and `POST /api/workflows` for a workflow outside its grants (`POST` cannot create a new workflow either), sees only its granted workflows in `GET /api/workflows`, and is refused on `/api/credentials`. Admin tokens and tokens with no grants are unchanged. Give such a token the grants it needs, or use an unrestricted token; see [Per-token workflow ACL](docs/operations/server-api-reference.md#per-token-workflow-acl)
- **Breaking** for scripts that removed a token's last workflow grant to make it unrestricted (`aerini-server`, `api`): `DELETE /api/tokens/:id/workflows/:workflow_id` now returns `409` and removes nothing when the grant is the token's only one, instead of leaving the token with no grants, which means unrestricted. To cut a token off, revoke it with `DELETE /api/tokens/:id`; for an unrestricted token, create a new one without `workflow_ids`. Removing one of several grants, or a grant the token does not hold, still returns `200` with `{"ok": true}`. The grant and list responses' `note` text no longer describes the ACL as covering only SSE events.
- `aerini-server` (`api`): rate-limit `429` responses now carry a JSON `{"error": ...}` body and a `Retry-After: 60` header instead of an empty body.
- Chat panel: restyled for legibility and accessibility. The "not running" banner now has a visible amber background and left edge, and its **Start** button no longer inherits the full-width primary-button style (which could squeeze the banner text); your messages and the Send button use a darker blue so white text meets 4.5:1 contrast on the dark theme; the message box and attach button have outlines that stand out against the panel, and the attach button's disabled state is more legible; Send, attach, and **Start** are at least 44 px tall, and the message box shows a keyboard focus ring; the message box and icon-only buttons are labelled for screen readers; the panel's slide-in and typing animations are skipped when the OS reduce-motion setting is on
- Chat panel: the "not running" banner and the empty-conversation notice are now one notice, and its wording says "press Start" instead of "use Start below". Filled primary buttons (Start, the onboarding example button, and similar) now use white text on the Paper theme, where the previous black text was below 4.5:1 contrast; the dark theme is unchanged. The session menu's delete control is now a real button reachable by keyboard, and small in-message controls (Copy, image overlay buttons, chip remove) have larger touch targets
- Chat panel: history is saved incrementally — sending a message writes only that message instead of the whole conversation (including image and attachment data), and only the open conversation is loaded when the panel opens. Large histories open faster, and switching to another session loads it on demand, briefly showing "Loading conversation…"; if that load fails, you stay in the current session.
- Run History: a run whose Webhook trigger received chat attachments stores the attachment data once instead of twice, so those runs take roughly half the space. Runs read back unchanged (including Replay). An older build opening a database written by this one shows a `{"$same_as": "files"}` placeholder in `body.attachments` of such runs

### Fixed
- Canvas (desktop): undo and redo no longer misbehave around multi-step edits. Deleting several nodes, duplicating several, placing a node onto a wire, and dropping a wire on empty canvas to add a node each undo in one step; before, they took one press per node or per piece. Dragging an existing node onto a wire and undoing deleted the node, and undoing a connection to AI Prompt's Files port or Image Generation's Reference Images port wiped any expression you had typed there; both now restore what was there. Undo history no longer carries over when you open another workflow, and undo is ignored (with a notice) while you are mid-drag
- Canvas (desktop): dropping a node onto a wire that feeds AI Prompt's Files port, Image Generation's Reference Images port, or a Save to Folder or Collect Files input left that input's expression pointing at the node the wire used to come from, so the inserted node's output was ignored. The expression now points at the inserted node, and undo and redo restore it
- `aerini-server` (`api`, `serve`): per-IP rate limits, including the widget `trigger` and `mint-token` limits, are now applied per IPv6 /64 instead of per address, so a client with an IPv6 prefix can no longer get a fresh budget by changing its source address; an IPv4-mapped IPv6 address now shares its IPv4 address's budget. IPv4 clients see no change.
- Desktop app: links to a web page did not open anything when clicked: **Support on Patreon** and **View on GitHub** in Settings, **View release notes** and **Download from GitHub** under Updates (the fallback when Aerini can't install an update itself), and the setup links in the Webhook and Social Upload panels. They now open in your default browser. Only a fixed list of Aerini-related HTTPS addresses opens; any other link, such as one in an AI reply, is blocked with a notice instead of navigating the app away. See [Security](docs/guide/security.md#opening-links)
- Running with parallel execution on: a Merge after an If, Switch, or other branching node never ran when one of its incoming branches was not taken, so everything after it was silently skipped and the run still reported success. It now runs once the branches that were taken have finished, as in a sequential run, and still waits for a branch that is only slow or has not started yet
- Importing a workflow file left the toolbar stale: the **Chat** and **Run on launch** buttons stayed hidden, and the Run button state stayed that of the previous workflow, until you clicked a node. They now update as soon as the import is confirmed
- AI Prompt and AI Agent: with Provider left on `auto`, the **Use Saved Credential** dropdown no longer hides credentials that have an Advanced Provider set (such as a Gemini key), which left the list empty until you changed Provider by hand
- **Breaking** for anyone who deleted the credential key to reset it (desktop app and `aerini-server`): when credentials are saved and Aerini cannot read the encryption key, it no longer quietly creates a new one that cannot decrypt them. On macOS this could happen after clicking **Deny** on the Keychain prompt, and left old credentials unreadable while new ones used a different key. The desktop app now shows an error and closes without changing anything; `aerini-server` exits with an error. To start empty on purpose, delete `credentials.db` too. A fresh install is unaffected. See [Credentials](docs/guide/credentials.md#if-aerini-cant-read-the-key)
- Desktop app: if the workflow database can't be opened at startup, Aerini now shows an error with the reason and closes, instead of crashing with no message
- Plugins: a trigger plugin built with `wasip3` (WASI 0.3) now loads in the **Plugins** panel instead of failing with "WASM linker setup or pre-instantiation failed: store configuration requires that `*_async` functions are used instead". Its `describe()` and `execute()` now run on the async engine, with the same 30-second limit, and a trigger plugin that spins without yielding is stopped there too; resolving a trigger to start it hit the same error and is fixed the same way. Plugins with an import neither engine provides are rejected at load, as before; see `docs/development/plugin-authoring.md#trigger-plugins`
- SSRF protection: IPv6 addresses that embed an IPv4 address (NAT64 `64:ff9b::/96`, 6to4 `2002::/16`, and `::a.b.c.d`) are now checked as that IPv4 address, as IPv4-mapped ones already were, so they can no longer reach internal hosts; NAT64 to a public address still works. `0.0.0.0/8` and `240.0.0.0/4` are now always blocked. See `docs/guide/security.md#ssrf-protection`
- Wait: when a condition times out, the workflow now continues from the **Timed out** port; before, it always continued from **Done**, so nothing connected to **Timed out** ever ran. If nothing is connected to **Timed out**, it still continues from **Done**. See `docs/guide/nodes.md#wait`
- Schedule (cron): a value outside its field's range (such as minute `75`) is now rejected straight away with an error naming the field, instead of after a long search that ended in a generic message. A date that exists only in some years, such as `0 0 29 2 *`, now finds the next leap day instead of failing, and the search no longer blocks the scheduler. Month names are accepted only in the month field and weekday names only in the weekday field, a weekday range ending in `7` (such as `5-7`) now includes Sunday, and macros such as `@DAILY` are accepted in any letter case. See `docs/guide/nodes.md#schedule`
- Slack, GitHub, Notion, Stripe, Google Sheets, Telegram, AI Prompt, AI Agent and image-generation nodes: a failed request or an unreadable response no longer puts the request URL (including a Telegram bot token or a `?key=` query secret) into the node error, run history or logs; the underlying cause, such as a refused connection, is still shown.
- Webhook: a `port` given as text (such as `"8080"`) is now used instead of silently falling back to 3456, and a port that is not a whole number from 1024 to 65535 fails with `INVALID_PORT`. A `path` without a leading `/` gets one added, and a lowercase `method` such as `post` now matches. The same checks apply when a Webhook workflow is started in the background, where a port such as 66560 used to wrap around to 1024.
- File: a filename containing two dots in a row (such as `report..final.txt`) is no longer rejected as path traversal; only a real `..` path component is. A `write` or `append` whose parent folder can't be created now fails with the reason instead of a later, less clear error.
- Shell: a very long command containing non-ASCII characters no longer crashes the node while its log line is shortened.
- Social upload and the OAuth listener: provider responses are now read with the same 10 MB limit as the other nodes.
- Credential key file: when the desktop app and the server start together on one data folder, the second no longer overwrites the key the first just created, which would have made every saved credential unreadable.
- Telegram, Slack, GitHub, Notion, Stripe and Google Sheets nodes: an unparsable response no longer puts the request URL (including a Telegram bot token) into the node error, and response bodies are read with the same 10 MB cap as the AI nodes. A `429` from Telegram, Slack, GitHub, Notion, Stripe, Google Sheets, Discord or SendGrid is now retried by the scheduler. Discord and SendGrid error messages include at most the first 1 KiB of the provider's response.
- GitHub: `owner`, `repo` and `issue_number` are validated, so a value such as `../user` can no longer redirect the authenticated request to a different API path; Notion `update_page` validates `page_id` the same way. Invalid values fail with `INVALID_OWNER`, `INVALID_REPO`, `INVALID_PAGE_ID` or `MISSING_ISSUE_NUMBER`. See `docs/guide/nodes.md`
- Send Email: an `smtp_port` above 65535 is rejected with `INVALID_PORT` instead of being wrapped to a different port, and a username without a password (or the reverse) fails with `INCOMPLETE_CREDENTIALS` instead of silently sending without authentication. Webhook: a `port` above 65535 is rejected the same way (it used to wrap past the privileged-port check)
- Desktop Notification (Linux): a title or body starting with `-` is shown as text instead of being read as a `notify-send` option, and an unknown `urgency` fails with `INVALID_URGENCY`
- Network error messages from the HTTP Request, Telegram, Discord, AI Prompt, AI Agent, image-generation, OAuth, Stripe, Google Sheets and social-upload nodes no longer include the request URL. A failed request used to put the full URL, including a Telegram bot token, a Discord webhook token or a `?key=` query secret, into the node error, run history and logs.
- HTTP Request: repeated response headers such as `Set-Cookie` are now joined with `, ` in the `headers` output instead of only the last one being kept, and numeric or boolean values in the `headers` input are sent as text instead of being silently dropped. See `docs/guide/nodes.md`
- `aerini-server`: an `Authorization: Bearer` header with more than one space before the token is now accepted, as RFC 7235 allows, and a header with nothing after the scheme is treated as missing, in both `api` and `serve` mode.
- `aerini-server` (`api`): error responses no longer include database or ACL-lookup error text. A failed store or database call now returns `500` with `{"error": "internal server error"}` and the cause is written to the server log, as the credential routes already did. Workflow-run errors that describe the workflow itself (a failed node, a timeout, a missing credential) are still returned.
- `aerini-server` (`api`): `GET /api/health` no longer returns the bundled Node.js check's raw error (which could include the executable's path) to unauthenticated callers; it returns a fixed message and logs the cause once.
- `aerini-server` (`api`): `--data-dir` / `AERINI_DATA_DIR` expands `~` only as `~` or `~/...`, so `~other/x` is no longer rewritten to a path under your own home. On Windows it falls back to `USERPROFILE` when `HOME` is unset (the default `~/.aerini-server` used to resolve to `/root/.aerini-server`), and it exits with a clear message when neither is set.
- `aerini-server` (`api`): the token key file (`tokens.key`) is now created with owner-only permissions from the start on Unix instead of being restricted after it was written, and a startup failure (an unwritable data directory, a database that will not open) prints one error line instead of a panic.
- Desktop app: two video or audio files with the same filename in one output (for example several `output.mp4` results) no longer overwrite each other in the temporary media folder, so each plays its own file; an oversized payload is also rejected before it is decoded rather than after.
- `aerini-server` (`serve`): the status page's `Authorization: Bearer` run secret check now accepts the scheme in any letter case (`bearer`, `BEARER`), as the API mode already did, instead of rejecting it with `403`.
- `aerini-server` (`api`): the first-run token banner is now aligned around the generated token, and `http://[::1]` (any port) is accepted as a localhost CORS origin like `localhost` and `127.0.0.1`.
- `aerini-server` (`api`, `serve`): under a flood from many distinct client IPs (or many distinct widget workflow IDs), rate limiting no longer scans its whole table on every request, which slowed the server and blocked legitimate requests. Stale entries are now swept at most once per second. Each limiter tracks at most 50,000 keys at once; past that, unseen keys are let through unlimited until stale entries expire, and tracked keys stay limited. `POST /api/workflows/:id/run` also no longer queries the database on every run to prune its per-workflow locks once more than 1,000 exist.
- `aerini-server` (`api`): token and credential routes no longer send internal database error text to the client on a `500`; the detail is logged on the server and the response carries `{"error": "internal server error"}`. A rejected `POST /api/scheduler/:id/start` now returns a readable message (for example `workflow not found`) instead of a Rust debug dump.
- AI Prompt and AI Agent: a request whose prompt (or goal) resolves to empty but that has a readable attachment (for example a Chat message with only a file) no longer fails with "prompt field is required"; a default instruction is sent in place of the text. A prompt with no text and no readable attachment still fails as before; see `docs/guide/nodes.md`
- Chat panel: sending files when no node reads the Webhook's `files` output now shows a notice, since the model otherwise receives only the message text; see `docs/guide/chat-panel.md#attachments`
- Shell Command and Code (JS) nodes: on timeout, or when the run is cancelled or its workflow-level timeout fires, the command and everything it started (pipelines, background jobs, child processes) are now killed on macOS and Linux, where before only the command's own process was; such processes could keep running after the run ended. The command now runs in its own process group. On Windows only the command's own process is killed, as before
- Shell Command and Code (JS) nodes: `timeout_secs` now also covers reading the command's output. A command that left a background process holding its output open (for example `sleep 300 &` with no redirect) used to keep the node waiting past the timeout until that process exited; it now times out and the process is killed
- Database node: a running SQLite statement is now interrupted, and a running Postgres or MySQL `Execute` statement (in runs that support cancellation, as API and desktop runs do) is cancelled on the server, when the run is cancelled or times out, instead of running to completion. The MySQL cancel watcher no longer stays alive after a run that times out
- `aerini-server` (`api`): token lookups, ACL lookups, credential operations and the scheduler stop on workflow delete no longer block the async runtime, so slow database access no longer stalls other requests.
- `aerini-server` (`api`): shutdown no longer waits indefinitely for open `/api/events` streams. It ends them as soon as the signal arrives and closes any remaining connections after 10 seconds, then drains in-flight workflow runs as before; previously `docker stop` or `systemctl stop` could end in SIGKILL before that drain ran. Clients see the stream end, and events emitted while disconnected are not replayed on reconnect; see [Events (SSE)](docs/operations/server-api-reference.md#events-sse)
- `aerini-server` (`api`): the global rate-limit `429` now carries CORS headers, so browser clients on an allowed origin can read it instead of seeing an opaque network error; and the rate limiters no longer risk a panic within the first minute after a Windows or macOS boot.
- `aerini-server` (`api`): `GET /api/workflows/:id` returns `500` if the workflow cannot be serialized instead of `200` with an empty body; `POST /api/tokens` returns `400` for an `expires_in_secs` too large to represent instead of panicking; the `Bearer` scheme in `Authorization` is now matched case-insensitively.
- Plugins: a workflow whose trigger is a plugin now actually starts when run in the background. The scheduler was never given the plugin directory, so every plugin trigger failed at once with "no plugin directory is configured" and the job showed as failed. The desktop app uses the plugin directory from Settings (changing it applies to the next start), and `aerini-server` uses `--plugin-dir`
- Plugins: a trigger-capable plugin as a workflow's entry node is no longer rejected by the editor. Run no longer stops with "No trigger node found", and starting the workflow in the background no longer says it has no Schedule or Webhook trigger. A plugin trigger only starts its own events when the workflow is started in the background; Run executes it once as an ordinary step
- Plugins: a trigger plugin that spins in `describe()` or `execute()` no longer ties up a runtime thread until the 30-second limit; the host now yields to the runtime about once a second while it runs, still stopping it at 30 seconds with the error "plugin ran for 30s without returning and was stopped". When starting a trigger, each plugin file in the directory now gets the same 30 seconds to instantiate and `describe()`, no further file is started once the scan has run for 90 seconds, and a file that does not finish is skipped and named, with the limit it exceeded, in the start error instead of hanging the start. A plugin file with an invalid signature is now skipped during that scan without being compiled or run, as it already was when loading. A trigger plugin that keeps failing or being stopped is restarted after a growing pause (5 seconds, doubling to 5 minutes, reset after a run that delivers an event or lasts a minute) instead of every 5 or 30 seconds, and the same error is logged at most every 5 minutes. A running trigger plugin that executes for 30 seconds without calling a WASI, HTTP, storage or file-watch import and without delivering an event is now stopped and reported as a trigger error; one that is idle between events is not affected; see `docs/development/plugin-authoring.md#trigger-plugins`
- Plugins: a trigger plugin that imports a WASI Preview 3 interface now has its `execute()` run (on the trigger engine, with the same 30-second limit) when the node runs as a workflow step, instead of the node returning an empty object without calling it
- Discord: the 2000-character message limit is now counted in characters instead of bytes, so a message of up to 2000 characters in a non-Latin script or with emoji is no longer rejected as too long

### Security
- Desktop app: approving the confirmation shown before running a Shell Command, Code, Database or plugin node no longer carries over to a changed node. The approval used to be remembered by workflow and node id alone, so after you approved a workflow, editing one of those nodes' settings, re-importing or reloading a modified file with the same ids, or restoring an older version ran the new settings with no prompt. It is now tied to each node's type, settings, saved credential and enabled state, so any change to one of them asks again, while an unchanged workflow still asks once per session. Only a hash of the settings is kept, never the values. Moving or renaming a node does not ask again. See [Nodes Reference](docs/guide/nodes.md#shell-command)
- Desktop app: **Replay** in run history ran the whole workflow, including Shell Command, Code, Database and plugin nodes, without the confirmation that Run, Run this node and a node's Test button show. It now asks first, like they do. See [Nodes Reference](docs/guide/nodes.md#shell-command)
- Desktop app: the confirmation shown before running a Shell Command, Code, Database or plugin node now names each node's type next to its name, so a workflow file can no longer hide one of these nodes behind a harmless-looking name such as "Weather lookup".
- Social Upload: a file's `mime_type` containing line breaks or other control characters is now replaced with `application/octet-stream` instead of being copied into the YouTube upload request, where it could add extra headers to the file part.
- Desktop app: the Summary tab of a run result now escapes a node's type name before showing it, so a workflow file with a crafted node type can no longer inject markup into the results panel.
- Desktop app: the content security policy now also sets `object-src 'none'`, `base-uri 'self'` and `form-action 'self'`. Browsers do not apply `default-src` to `base-uri` or `form-action`, so injected markup could previously add a `<base>` tag or submit a form to another origin. The app itself uses none of these, so nothing changes in normal use.
- `aerini-server` (`api`): the public widget routes (`POST /api/widget/:workflow_id/trigger` and `mint-token`) no longer return internal error text to unauthenticated callers. A database failure, a corrupt trigger row, or a failed relay call used to put SQL or parser messages, or the loopback URL and port of the workflow's Webhook listener, in the response body; they now return a generic message (`internal server error`, or the existing "could not reach the workflow's webhook listener" text) and log the detail server-side.
- `aerini-server` (`api`): with `--trusted-proxy-count` set, only the first `X-Forwarded-For` header line was read, so a proxy that appends its own line instead of extending the client's let a client choose the IP used by the per-IP rate limits. All header lines are now read as one list, and the Nth entry from the right is used as before. Single-line deployments see no change.
- `aerini-server` (`api`): a token restricted by the per-token workflow ACL could still list, read, delete, run, create or overwrite any workflow, and use the server-wide credential routes, limited only by its `read`/`write` scope. Those routes now enforce the ACL; see Changed above.
- `aerini-server`: `--trusted-proxy-count` picked the wrong `X-Forwarded-For` entry, one position too far left, so a client could put its own address at the front of the header and have that used as its IP by the per-IP rate limits (including the widget trigger and `mint-token` limits) and the status page. The Nth entry from the right is now used, as each trusted proxy appends its peer's address. Deployments that already matched their proxy count to their topology see no change for well-formed requests.
- `aerini-server`: a token whose stored expiry cannot be parsed is now rejected instead of never expiring.
- Debug tab: the node id fragment shown in each log line is now HTML-escaped before being inserted into the panel, matching the message text next to it. Verified exploitable: node ids are taken as-is from imported workflow JSON with no validation, so a crafted `id` value could inject markup into the Debug tab once a log entry referenced that node
- Embeddable chat widget (`aerini-widget.js`): session-id generation now tries `crypto.getRandomValues()` before falling back to `Math.random()` for the last `data-session-id` (CWE-338) — closes the gap between `crypto.randomUUID()`, tried first, and the previous direct-to-`Math.random()` fallback. The session id is stored in `localStorage` and sent to the target workflow's Webhook trigger as `session_id`, where it commonly keys per-visitor state (e.g. an AI Memory node, as in `examples/Chatbot + AI Memory + Widget.md`); a `Math.random()`-derived id is predictable enough that another visitor could guess it and inject messages into someone else's conversation thread on a browser/runtime that lacks `crypto.randomUUID` but still has the older, more widely supported `crypto.getRandomValues`
- Plugins: the plugin inspection step now checks a plugin's signature before compiling it or running its code, as loading already did; a file whose signature sidecar is invalid is rejected and shows a load error in Settings. Trigger plugins' `describe()`/`execute()` calls are now also stopped by a CPU deadline, so a guest that never yields cannot hang them
- Plugins: a trigger plugin whose `events()` call or event stream spins without yielding can no longer hold a runtime thread forever or ignore the job's stop. A running trigger now yields to the runtime about once a second, and one that goes about 30 seconds with no WASI or HTTP call and no delivered event is stopped and reported as a trigger error; a trigger that is simply idle between events is not affected. See `docs/development/plugin-authoring.md#trigger-plugins`
- Shell Command: the command line written to the run log now redacts an `Authorization` header value written in single quotes (`-H 'Authorization: Bearer ...'`) or without quotes. Only the double-quoted form was redacted before, so a token in a single-quoted header was saved in the run log in plain text. The closing quote after a redacted double-quoted header is also kept now, so the logged command reads as it was written. Run logs saved earlier are not rewritten; review them if a workflow used the single-quoted form.
